Generic server error — low cognitive-load designs

One screen for any unexpected server error. The user never has to decode what broke — no status codes, no jargon, no branching. Every variant does three things: takes the blame off the user, gives one clear way forward, and keeps a support reference quietly available for whoever needs to debug. Same design language as the payment screens.

How these keep cognitive load low

  • One screen for every server error — 500, 502, 503, timeout, unknown: the user sees the same calm message regardless. No error taxonomy to interpret.
  • No codes in the headline — the HTTP status never reaches the user. The quiet “Ref: 7F3A‑2C91” is a random per-incident ID for support to trace logs, not a technical error the user must understand.
  • Blame is removed — “on our side”, “it’s not you”, “our system”. The user never wonders if they broke something.
  • One primary action — a single Retry. Support is always secondary/ghost so the obvious path stays obvious.

Recommendation

  • Ship A · Something went wrong as the default — it’s the most universally understood and the lowest-load.
  • Wire in D · Auto-retry behavior underneath it: attempt a silent retry with backoff first, and only fall back to A’s manual screen if that fails. Best of both — most transient blips resolve without the user ever seeing an error.
  • Keep the reference code on all variants (map it to your log/trace ID) but visually quiet, exactly as shown.
